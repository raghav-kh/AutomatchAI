# AutoMatch AI — Backend (Phase 1 + 2 + 3 + 4)

AI-powered car recommendation & decision support system.

- **Phase 1**: data model, CRUD API, pipeline metadata scaffolding.
- **Phase 2**: the ingestion pipeline — API detection, scraper framework, dispatcher.
- **Phase 3**: the recommendation engine — scoring, confidence, explainable
  reasons/trade-offs, Groq-based explanations with a consistency guard.
- **Phase 4 (this update)**: ownership cost calculator, smart comparisons,
  and alternative recommendations (SRS 4.5, 4.6, 4.7).

## What's in Phase 4

- **`recommendation/ownership_cost.py`** (SRS 4.5) — `GET /variants/{id}/ownership-cost`.
  Purchase price, insurance (front-loaded, declining ~10%/yr), fuel cost
  (mileage × annual km × fuel price, with an India-average default per fuel
  type, overridable), maintenance (scaled off `AIAttributes.maintenance_level`),
  a flat road-tax estimate, and expected resale (scaled off
  `AIAttributes.resale_value` against a standard depreciation curve).
  Every assumption used is returned in the response's `assumptions` field —
  nothing is a hidden constant.
- **`recommendation/comparison.py`** (SRS 4.6) — `GET /compare?variant_ids=1&variant_ids=2...`.
  Side-by-side rows across performance, safety, maintenance, boot space,
  ground clearance, and an **AI recommendation score** computed with
  *neutral* preferences (budget = the variant's own price, so nothing gets
  penalized for cost) — a context-free quality signal distinct from the
  personalized `/recommendations` score.
- **`recommendation/alternative.py`** (SRS 4.7) — `GET /variants/{id}/alternatives`.
  Finds variants in the same body type and a ±20% price band that clearly
  outperform the reference on refinement, resale, reliability (inverse of
  maintenance_level), highway/city comfort, or service network — and only
  lists a reason where the margin is meaningful. Excludes trims of the same
  car (an "alternative" should be a genuinely different model). Live-tested
  against the SRS's own example: XUV 3XO → Honda Elevate, with the exact
  reasons "Better refinement / Better resale value / More reliable" coming
  back correctly ranked.

## Explanation consistency guard (also added this round)

**`recommendation/explanation_guard.py`** — the LLM explains, the scoring
engine decides. If a Groq-generated explanation praises something the
scoring engine flagged as a trade-off for that variant (e.g. calls a
service network "excellent" when `service_network` scored ≤4.5), the guard
rejects it and falls back to the template explanation instead of surfacing
a contradiction. Coarse keyword/proximity heuristic, not semantic — catches
the clear cases cheaply without a second model call.

## Running locally (SQLite, fastest)

```bash
python -m venv venv && source venv/bin/activate
pip install -r requirements.txt
cp .env.example .env
# Optional: set GROQ_API_KEY in .env for LLM-generated explanations.
# Without it, recommendations still work fully -- explanations use the
# template fallback instead.

alembic upgrade head
python -m scripts.seed_demo_catalog   # populates a full working demo catalog
# (or scripts.seed_manufacturers for just names, no cars/variants)

```

Visit `http://localhost:8000/docs` for interactive Swagger docs. With the
demo catalog seeded, try the SRS's own example immediately:

```bash

  -H "Content-Type: application/json" \
  -d '{"budget": 1000000, "body_type_preference": "SUV"}'

```

## Running against Supabase (Postgres)

1. Create a project at [supabase.com](https://supabase.com).
2. In **Project Settings → Database → Connection string**, copy the **URI**.
   Use either:
   - **Session pooler** (port 6543) — recommended, works well for typical
     backend workloads.
   - **Direct connection** (port 5432) — simpler, fine for a single
     long-lived process like this API.
3. Rewrite the scheme from `postgresql://` to `postgresql+psycopg://`
   (this project uses the psycopg3 driver, not the legacy psycopg2) and set
   it as `DATABASE_URL` in `.env`. See `.env.example` for the exact shape.
4. Run migrations against it:

```bash
pip install -r requirements.txt
cp .env.example .env   # then set DATABASE_URL to your Supabase URI
alembic upgrade head
python -m scripts.seed_manufacturers   # optional
uvicorn app.main:app --reload
```

That's it — no local database container needed. `app/core/database.py`
already disables server-side prepared statements for Postgres connections,
which avoids a common pgbouncer/transaction-pooler gotcha if you use the
Session pooler connection string.

## Data sourcing workflow (Phase 2, unchanged)

1. Seed manufacturer **names only** (`scripts/seed_manufacturers.py`).
2. `POST /pipeline/classify-pending` probes for open APIs, sets
   `data_source_type` + `confidence_score`.
3. Assign a `scraper_module` for scraper-classified manufacturers.
4. `POST /pipeline/manufacturers/{id}/ingest` runs it, upserts
   `Car`/`Variant` with provenance.
5. `GET /variants/stale?days=90` surfaces variants due for re-verification.

## Real scraper: Tata Motors (this update)

`app/pipeline/scrapers/tata.py` is a **real, working scraper** against
`cars.tatamotors.com` — not the hypothetical template. It's grounded in an
actual captured page (`tests/fixtures/real_pages/tata_nexon_price_page.txt`)
and tested against it.

**What it gets right**: variant names (e.g. "Smart + AMT 1.2", "Fearless +
PS DT 1.2") and their full feature lists, both genuinely present in the
page's static content. Fuel/transmission/engine displacement are inferred
from the trim name itself — real signal in Tata's naming convention
("CNG" in the name → CNG, "AMT" → Automatic, "1.5" → the 1.5L diesel,
"1.2" → the 1.2L petrol).

**What it honestly can't get, and why**: exact ex-showroom prices.
`cars.tatamotors.com` resolves prices client-side once a city is selected
— the static page never contains a number, only "Offer Price" / "Monthly"
placeholders. Every `ScrapedVariant` this produces has `price=None`. Two
real ways to close that gap, neither built yet:
1. A headless browser (Selenium/Playwright) that picks a city and waits
   for the async price call — the SRS's own tech stack already
   anticipated this ("Selenium (only if necessary)").
2. Fill price manually via the Catalog UI/API after ingestion, using the
   variant names the scraper already gives you.

**Also worth knowing**: the site has bot detection. A plain `requests`
call without a realistic User-Agent (already set here) can still get
blocked (403) intermittently, and bursts of requests make it worse. When
that happens, `run_ingestion_for_manufacturer` catches it and logs a
`failed` ScrapeLog with the real error — verified live: an ingestion
attempt from this project's own sandboxed network came back
`403 Client Error: Forbidden`, and it failed cleanly rather than crashing
or silently losing data. Run it from a normal environment (not this
sandbox, which restricts outbound network to package registries only) to
actually pull live data.

To use it: `PATCH /manufacturers/{id}` with
`{"scraper_module": "app.pipeline.scrapers.tata.TataScraper"}`, then
`POST /pipeline/manufacturers/{id}/ingest`.

## Admin auth (this update)

Every write endpoint — creating/editing/deleting manufacturers, cars,
variants, and both pipeline triggers (`classify-pending`, `ingest`) — now
requires a bearer token from an admin account. **Read endpoints stay
public**: browsing the catalog, `/recommendations`, `/compare`,
`/variants/{id}/alternatives`, and `/variants/{id}/ownership-cost` need no
auth at all.

This is deliberately scoped as an *internal admin* auth layer, not the
SRS's future "user accounts" feature (§11 — buyer-facing saved searches
etc., still unbuilt). It answers "who's allowed to write to the catalog,"
not "how do buyers log in."

**Getting a token:**

```bash
# 1. Register (requires ADMIN_SETUP_KEY from your .env)
curl -X POST http://localhost:8000/auth/register \
  -H "Content-Type: application/json" \
  -d '{"username": "raghav", "password": "<a real password>", "setup_key": "<your ADMIN_SETUP_KEY>"}'

# 2. Log in (form-encoded, not JSON -- it's OAuth2PasswordRequestForm)
curl -X POST http://localhost:8000/auth/login \
  -d "username=raghav&password=<your password>"
# -> {"access_token": "...", "token_type": "bearer"}

# 3. Use it
curl -X POST http://localhost:8000/manufacturers \
  -H "Authorization: Bearer <access_token>" \
  -H "Content-Type: application/json" \
  -d '{"name": "Tata Motors"}'
```

In `/docs`, click **Authorize** and paste the token — Swagger handles the
header for you from there.

**Design choices, and why:**
- **bcrypt** for password hashing, **PyJWT** for tokens (HS256, 24h expiry
  by default — override via `ACCESS_TOKEN_EXPIRE_MINUTES`).
- **No public sign-up.** `POST /auth/register` requires `ADMIN_SETUP_KEY`
  to match, compared with `secrets.compare_digest` (constant-time, avoids
  timing attacks) rather than `==`.
- **Every account is an admin account** (`is_admin=True` always) — there's
  no regular-user tier yet, so a role system beyond a boolean would be
  premature.
- **Startup warning, not a hard failure**, if `SECRET_KEY`/`ADMIN_SETUP_KEY`
  are still the insecure defaults while `ENVIRONMENT != development` — logged
  loudly so it's impossible to miss in production logs, without blocking
  local dev.
- **Password hash never leaves the server** — `UserOut` doesn't include it,
  checked explicitly in tests.

**Testing note:** `tests/conftest.py`'s default `client` fixture bypasses
auth (overrides `require_admin` with a fake admin) so the other ~75 tests
didn't need touching. Real auth behavior — registration gating, login,
token validation, 401s on protected routes, public routes staying public —
is exercised end-to-end in `tests/test_auth.py` via a separate `raw_client`
fixture that does *not* bypass auth.

## API-based ingestion (this update)

Manufacturers classified `data_source_type=api` previously had no actual
ingestion path — the dispatcher only knew how to call `.scrape()` on an
HTML scraper. Now it handles both uniformly:

- **`app/pipeline/scrapers/base.py`**: `BaseApiClient(BaseScraper)` — same
  `scrape() -> list[ScrapedCar]` output contract as a scraper, but takes
  `api_endpoint` at construction time instead of hardcoding a target URL,
  since for API-classified manufacturers the endpoint is discovered (or
  manually set) per-manufacturer and lives on `Manufacturer.api_endpoint`.
- **`app/pipeline/dispatcher.py`**: `_instantiate_ingestion_source()`
  loads whatever class `scraper_module` points to, then checks
  `issubclass(cls, BaseApiClient)` to decide how to construct it — a
  manufacturer's `data_source_type` doesn't have to be trusted for this;
  the class declares what it needs. If it's a `BaseApiClient` and
  `api_endpoint` isn't set, ingestion fails cleanly with that reason
  logged to `ScrapeLog`, rather than crashing.
- **`app/pipeline/scrapers/nhtsa_vpic.py`**: `NhtsaVpicApiClient`, a real,
  working adapter against NHTSA's public vPIC API (free, no auth,
  verified live — see `tests/fixtures/real_pages/vpic_aston_martin_models.json`,
  a genuine captured response). Reusable across any make by just changing
  the `api_endpoint` URL stored on the `Manufacturer` row.

**Honest limitation, same spirit as the Tata scraper**: vPIC is a
compliance/VIN-decoding database, not a commercial pricing catalog — it
gives real canonical Make/Model names but no trims, variants, or price.
Every car it produces has one placeholder `ScrapedVariant` with
`price=None`. It's also **not an Indian-OEM API** — vPIC only covers
vehicles certified for the US market, so Tata/Mahindra/etc. won't appear
in it. This demonstrates the `BaseApiClient` pattern is real and working,
not that vPIC solves your actual catalog — a real Indian-manufacturer API
adapter would follow this same shape once one is identified.

Live-verified: triggering ingestion via `POST /pipeline/manufacturers/{id}/ingest`
against a manufacturer configured with the vPIC adapter correctly
attempted the real HTTP call and logged a clean failure when this
sandbox's restricted network blocked it — same resilience pattern as the
Tata scraper.

## Demo catalog (this update)

`scripts/seed_demo_catalog.py` populates a realistic, presentation-ready
catalog — 7 manufacturers, 12 cars, 13 variants, each with full
specifications and AI attributes — so every feature has real results to
show instead of empty states. Idempotent (safe to re-run).

Deliberately recreates the SRS's own examples, verified live:
- **"SUV under 10 lakh" (SRS §1)**: `{"budget": 1000000, "body_type_preference": "SUV"}`
  → Tata Nexon (₹9.5L, 85% confidence) and Citroën Basalt (₹9.5L, 76%
  confidence) both surface, exactly as the SRS's problem statement describes.
- **"Family of 7" → 7-seater wins**: `{"budget": 3000000, "family_members": 7}`
  → Mahindra XUV700 (the only 7-seater in the catalog) ranks first.
- **Short commute penalizes EV** (SRS §4.8): `{"budget": 2000000, "daily_running_km": 8}`
  → the Nexon EV's `fuel_match` score drops to 4.0/10, exactly matching
  the SRS's "hybrid may not be financially beneficial" guidance.
- **"XUV 3XO → Honda Elevate" (SRS §4.7)**: `GET /variants/{xuv_3xo_id}/alternatives`
  → returns the Elevate first, with the reasons "Better refinement / Better
  resale value / More reliable, lower maintenance" — the SRS's example verbatim.

Also spans multiple confidence tiers (manufacturers ranging 0.4–0.9) and
both `data_source_type` values (`scraper`/`api`), so `/recommendations`'
confidence blending and the pipeline's classification split both have
something real to demonstrate.
